# EWay Bill API Reference — Masters India GSP (Enterprise Solution)

**Source of truth:** `data/gsp-pdfs/ewb-api-spec.txt` — the OCR/text extraction of
*"EWay Bill API Document - Enterprise Solution"*, Company Confidential, MASTERS INDIA PRIVATE LIMITED
(59 PDF pages, 3,201 extracted lines). Every URL, JSON key, enum value and error string below is
copied verbatim from that file. Nothing has been invented.

**Reading rules used in this document**

- ❗ = a gap, mismatch or discrepancy in the source that an integrator must resolve before coding.
- "example only" = the key appears in the document's sample payloads but is **not** in the
  parameter table, so the document gives **no** type, size or mandatory flag for it.
- The document contains **no** consolidated error-code table, **no** production URL, **no** rate-limit
  or IP-whitelisting section, and **no** by-IRN generation endpoint. See §14.
- All 31 code blocks are shown with the document's own casing — which is inconsistent
  (`Method: POST` vs `Method: Post`; `"Regular"` vs `"r"`; `"Road"` vs `"road"`). Do not "normalise"
  these when coding; send exactly what the endpoint's example shows.

Note: the failure envelope is **not** the `results`/`nic_code` envelope — it is a flat
`{"error": "..."}` object with no numeric code and no `status`.

### Auth header on every subsequent call — exact format

The document writes it as:

```
header 'Authorization: JWT eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...'
```

i.e. the scheme is the bare word **`JWT`** followed by a single space and the raw token.
**It is not `Bearer`.** (Every operation from #2 onward shows this header, including the GETs.)

### Token lifetime

❗ The document **does not state a lifetime**. It only ships sample JWTs whose payload contains
`exp` and `orig_iat`. Derived from the document's own #1 sample token payload
(`{"user_id":646,"username":"aman@mastersindia.co","exp":1694835564,"email":"aman@mastersindia.co","orig_iat":1694749164}`),
`exp - orig_iat = 86400 s = 24 h`. Treat 24 h as *observed in a sample*, not as a documented SLA,
and implement re-auth on 401/expiry rather than trusting it.

```json
{
  "results": {
    "message": {
      "ewayBillNo": 301009218802,
      "ewayBillDate": "15/09/2023 02:36:00 PM",
      "validUpto": "24/09/2023 11:59:00 PM",

      "url": "sandb-api.mastersindia.co/api/v1/detailPrintPdf/anVsX3NlcF8yMDIzLTI0-65041f35112f30081f9e0b3d/"
    },
    "status": "Success",
    "code": 200,
    "requestId": "ERP1694768948_IMP/23/032"
  }

```

- Envelope: **`results`** (object) → `message` + `status` + `code`, plus a sibling `requestId`.
- `requestId` format observed: `ERP<epoch-seconds>_<document_number>`.
- There is **no** `data` envelope anywhere in this API; the envelope is always `results`.
- ❗ There is **no** `EwbNo` / `EwbDt` / `EwbValidTill` / `EwbBillPdf` / `EwaybillPdf` / `QRCode`
  key in this document. The actual names are `ewayBillNo`, `ewayBillDate`, `validUpto`, and a
  **`url`** pointing at the PDF-print endpoint. If your downstream contract uses the `Ewb*` names,
  it must be mapped from these. No QR-code field is documented at all.

## 14. Response envelopes and the field-name glossary

### 14.1 The three envelope families

| Family | Shape | Seen in |
|---|---|---|
| **A. Business result** | `{"results": { "message": <object>| <array>| <string>, "status": "Success"\|"No Content"\|"Fail", "code": 200\|204, ...extras }}` | Almost every operation |
| **B. Flat error** | `{"error": "<text>"}` or `{"error": "...", "error_description": "..."}` | #1 token-auth, #25 bulk generate |
| **C. Bulk-array** | `{"results": [ { "message": {...}, "status": ..., "code": ..., "requestId": ..., "docNo": ... } ]}` | #25A, #26A |

- There is **no `data` key and no `results.data`** anywhere. The envelope root is always `results`.
- `status` values observed: `"Success"`, `"No Content"`, `"Fail"`.
- `code` is an **in-body** number (`200` / `204`). The document never states the HTTP status line —
  treat the body `code` as authoritative and tolerate a mismatch with the HTTP status.
- `results` may hold siblings alongside `message`: `status`, `code`, `requestId`, `request_status`,
  `request_id`, `docNo`, and (for #23) `distance`.

### 14.2 Name mapping for the fields the brief asked about

| Brief's assumed name | Actual key in this document | Where |
|---|---|---|
| `EwbNo` / `EwbNumber` | **`ewayBillNo`** (generate/cancel/reject/extend/transporterId responses), **`eway_bill_number`** (list responses), **`ewbNo`** (multi-vehicle + regenerate arrays), **`cEwbNo`** (consolidated) | throughout |
| `EwbDt` | **`ewayBillDate`** (generate), **`eway_bill_date`** (lists), **`cEwbDate`** (consolidated) | throughout |
| `EwbValidTill` / validity | **`validUpto`** (POST responses), **`eway_bill_valid_date`** (GET/list responses) | throughout |
| `EwbBillPdf` / `EwaybillPdf` | **`url`** — a path to `.../detailPrintPdf/<hash>/` or `.../consolidatePrintPdf/<hash>`; sometimes with `https://sandb-api.mastersindia.co` prefix, sometimes host-relative ❗ | #2, #4, #5, #9, #25A, #26A |
| `QRCode` | ❗ **No QR field exists in this document** | — |
| `alert` | **`alert`** — present in the generate-type responses (`""` on success) | #2, #25A, #26A, #16 |
| status message | **`status`** (`"Success"`/`"No Content"`/`"Fail"`) and **`message`** | all |

### 14.3 Other reference fields in responses

- `ewayBillNo` is `Number(12)`, `ewayBillDate` is `Text(22)` formatted `dd/mm/yyyy hh:mm:ss AM/PM`
  (from the parameter table).
- Document-number echo: generate success includes `requestId` = `ERP<epoch>_<document_number>`;
  bulk responses add `docNo`.
- `generate_mode` = `"API"` on fetched EWBs.
- `eway_bill_status` observed values: `"Active"` (fetched) and `"DIS"` (documented rule about
  Part-A-only EWBs older than 15 days).
- `reject_status`: `"Y"` / `"N"`; `extended_times`: integer; `number_of_valid_days`: integer.

### 15.3 ❗ Codes the brief asks about that are NOT in this document

The brief asks to flag duplicate / invalid-GSTIN / invalid-vehicle / invalid-PIN / auth-failure /
document-already-used. **The document gives no numeric code for any of these.** What it gives is
prose in the Validations section (§16):

- **Duplicate e-way bill / document already used** — described but uncoded: *"The system checks for
  the duplicate e-way bill on the same document number of the consignor… the system will not allow
  generating one more e-way bill on the same number."* and *"Generation of duplicate E-waybills for
  the same document by Consignee and Transporter is not allowed hence forth…"*. In the consignee/
  transporter case the doc says the system *will* generate it and raise an **alert** instead:
  *"the system will generate E Way Bill and alert through API … that already there is one e-way bill
  with that document number."* So duplicate handling is **alert-based, not code-based** — you must
  read `message.alert` on the success path, not only `nic_code` on the failure path.
- **Invalid GSTIN** — no code; only the validations *"fromGstin and toGstin should be valid GSTIN
  number… pass URP"*, *"In case of a cancelled GSTIN…"*.
- **Invalid vehicle number** — no code; only *"the format of the vehicle should be valid and as per
  the format"* and the `TMXXXXXX` temporary-registration rule.
- **Invalid PIN** — only the uncoded `"Invalid pin code"` from #23, plus the PIN/state validation
  prose.
- **Auth failure** — only `{"error": "Unable to login with provided credential"}`. ❗ The document
  never shows what an **expired/invalid JWT** returns on a business endpoint, so the 401 shape is
  unknown. Handle "no token / unexpected envelope" defensively.

### 15.4 Retryability

❗ The document does **not** label codes as retryable or fatal. The classification column in §15.2 is
engineering judgement layered on top of the source, not a documented attribute. Apply it as a
starting policy and instrument real traffic before trusting it.

## 18. Gaps, defects and risks to resolve before production

1. ❗ **No production URL exists in this document.** Only `sandb-api.mastersindia.co`. Confirm the
   production host with Masters India; do not guess `api.mastersindia.co`.
2. ❗ **No EWB-by-IRN operation.** Generation from an IRN is only mentioned as a *blocking rule*, and
   the remedy points at the E-Invoice system. Check `data/gsp-pdfs/einvoice-api-spec.txt`.
3. ❗ **No consolidated error-code table.** Only the 16 codes embedded in examples (plus the uncoded
   strings in §15.2). Real-world integration will hit codes not listed here.
4. ❗ **`#14 Get Transporter Details` has the same URL/action as `#13`.** Almost certainly a
   copy-paste defect. Verify the real `action` value.
5. ❗ **`transporter_id` is marked mandatory `Y` in the table** while the Part-A-slip rule implies it
   can be omitted on a value-based generation and requires `vehicleNo`/`transMode`/`transDocNo` blank —
   directly conflicting with those fields' `Y` flags.
6. ❗ **Item CESS key drift:** `cessNonAdvol` (#2, #7) vs `cessAdvol` (#25, #26).
7. ❗ **`requestId` vs `request_id`** across #25/#25A vs #26/#26A.
8. ❗ **`hsn_code`, `pincode`, `transportation_distance`, `transporter_document_number` change
   JSON type between requests and responses** (string ↔ number). Build lenient parsers.
9. ❗ **Two datetime formats for validity** (`… 11:59:00 PM` vs `… 23:59:59 `). Build a tolerant parser.
10. ❗ **Bulk generate's failure envelope is a different family** (`error`/`error_description`) from
    every business endpoint.
11. ⚠️ **Duplicate-document protection is partly alert-based** (`message.alert`), so success responses
    must be inspected, not just failures.
12. ⚠️ **No pagination** on the date-scoped list endpoints — plan for full-day result sets.
13. ⚠️ **No documented rate limit, IP whitelist, timeout or retry policy** — assume none is guaranteed
    and implement client-side concurrency control and idempotency on `document_number` yourself.
14. ⚠️ The validation section speaks NIC field names (`fromGstin`, `totInvValue`, `transDocNo`),
    which are **not** this API's JSON keys. Do not port them literally.
